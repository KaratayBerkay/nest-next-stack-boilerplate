## 1. Executive summary — the ten findings that matter most

1. **The `/auth/login` ⇄ `/v1/en/feed` loop is fully deterministic, not a race.** The automatic 401-handler (`onAuthLogout` in `next-js-boilerplate/src/features/auth/hooks/useAuth.tsx:113-130`) clears only in-memory React state and hard-navigates — it **never clears the BFF cookies**. The stale `session_user` cookie then convinces the next page load's server-side check (`getSessionUser()`) the user is still logged in, bouncing back to `/v1/en/feed`, which fails the same backend check again. (F21, Stage A)
2. **This app's "token refresh" doesn't refresh anything.** `/api/auth/token` (`next-js-boilerplate/src/app/api/auth/token/route.ts`) just echoes whatever's already in the cookie jar. The backend has a fully correct `refresh` GraphQL mutation (`auth-session.service.ts:52-138`) that the web frontend **never calls anywhere**. Once a session goes stale there is no repair path except a fresh login. (F22, Stage A)
3. **Concrete, code-confirmed triggers that desync a "valid-looking" cookie from the backend's opinion**: changing your subscription tier immediately rewrites every live session's RBAC token backend-side with no matching cookie update (F23); a UTC-midnight token-derivation cutover (F23); and a Redis refresh-index key whose TTL never slides with activity, so refresh capability would silently die 15 minutes after login regardless of usage even if a real refresh flow existed (F11, Stage E — fix together with Stage A).
4. **Two commits already landed 3 days ago (2026-07-28) attempting a narrower, MFA-specific fix** for a related session-key-mismatch bug (`3aff834d`, `c0982fa0`) — after convert-frontend-9's doc had already closed clean, so this was never verified by that doc's rounds. Backend unit tests for it pass (20/20, confirmed live this session), but it doesn't touch the general-case loop in #1/#2. (F25, Stage A)
5. **Billing has a critical financial bug.** Upgrading between two paid tiers (e.g. BASIC→MEDIUM) never cancels the old Stripe subscription before creating a new one, and overwrites the only stored reference to it (`billing.service.ts:56-169`) — the customer is billed for both, indefinitely, with no in-app way to stop the first one. (F13, Stage F)
6. **Billing invoice amounts are wrong by roughly 100x.** The Stripe webhook stores `amount_paid` (cents) divided by 100 as if that were the final amount (`stripe-webhook.controller.ts:97`); the frontend then divides by 100 again assuming cents (`InvoiceTable.tsx:98`). A $19.99 charge displays as **$0.20**. Zero test coverage exists for the webhook controller. (F17, Stage F)
7. **The avatar upload bug has two independent, stacked root causes.** `MINIO_PUBLIC_URL` is missing from the backend's Vault secret, so the URL-builder falls back to `http://minio:9000` — a Docker-internal hostname no browser can resolve (`minio.service.ts:22-25`). *Even after fixing the hostname*, `UpdateProfileInput.avatarUrl`'s `@IsUrl()` validation rejects any non-FQDN URL by default — confirmed directly against the installed `validator@13.15.35` package, `http://localhost:9000/...` fails too. The real fix needs an actual public domain wired through Vault, not a one-line hostname swap. (F5, F6, Stage C)
8. **Feed comments have two independent bugs, not one.** Replies are structurally excluded from the feed's post query — an unconditional `parentId: null` Prisma filter (`post.service.ts:205-207`) that never selects `parentId` at all. This is permanent, not a timing issue. Separately, a 3-layer, never-invalidated cache stack (browser `Cache-Control`, Next.js server fetch-cache, Redis) sits in front of the same read path specifically on the feed page, explaining why even a hard reload doesn't help. (F26, F27, Stage G)
9. **The friend-request live-update bug is a scoping mismatch, already half-fixed by existing code.** The event uses page-scoped delivery (`emitToPage`, targeting a `"friend-request"` page claim) but the Messages page claims `"messages"` — the frame is silently dropped for anyone there. The frontend's invalidation logic (`renew-dispatch.ts:85-91`) is already correct and just needs the event to arrive; switching to the same non-page-scoped delivery already used for notifications and new messages fixes it. (F1, Stage B)
10. **The chat-nickname feature doesn't exist end-to-end, on either platform** — this is a build item, not a wiring bug. The privacy settings page's save handler builds a payload and never sends it to any API, on **both** Web and Flutter. Even if it did, no nickname field exists anywhere in the Prisma schema or the WS presence payload. (F4, Stage B)

**A cross-cutting pattern worth naming once, since it independently recurs in three unrelated places:** an authenticated, per-user, mutable GraphQL read gets proxied through a BFF route that defaults to `next: {revalidate: 60}` unless the route explicitly opts out with `noCache: true` (`lib/backend.ts:244-273`) — and only `auth/login`'s route does, anywhere in the app. This same omission independently produces stale reads in feed comments (F27), the sessions list (F11), and — per Agent C's report — `api-keys/route.ts` has the identical gap. See §3's open decision: patch each call site, or flip the shared helper's default.

## 2. Findings (full detail)

Each finding is tagged **Confirmed** (established by directly reading the current code, no live check needed to trust it) or **Plausible** (a concrete, code-grounded hypothesis that would benefit from a live/runtime check before treating as fully settled).

### 2.1 Messaging & chat-room

**F1 — Friend-request live-update never reaches the Messages page.** Confirmed. Friend send/accept/decline logic lives in `MessagingFriendService`/`MessagingController` (`nest-js-boilerplate/src/messaging/`), not the `friends` module (which is read-only and emits nothing). On accept, `messaging.controller.ts:103-119` calls `this.realtime.emitToPage(userId, 'friend-request', {renew:'Friends', type:'PendingList'})`. `emitToPage` (`realtime.gateway.ts:601-621` → `realtime-page.manager.ts:217-235`) only delivers to sockets whose page-claim key is literally `page:friend-request:{userId}:*`. Per `next-js-boilerplate/src/lib/realtime/route-mapping.ts:10-17`, `/v1/en/messages` claims page `"messages"`, while only `/v1/en/find-friends` claims `"friend-request"` — two different keys, so a user on Messages never receives the frame. The frontend's consumer (`renew-dispatch.ts:85-91`, invalidating `["friends","requests"]` and `["friends","list"]`) is already correct and would work immediately once the frame arrives. Contrast: the notification bell updates because `NotificationService.create` uses `emitToService(userId, 'NOTIFICATION', ...)` — not page-scoped, delivered to every connected socket regardless of current page (every client registers for it unconditionally on connect, `useRealtimeCoordination.ts:89,217`). New-message renews use the same broad pattern (`messaging-dm.service.ts:216-230`). Friends is the one outlier still using page-scoping.
*Secondary factor:* `friendsQueryOptions()` has no `staleTime` override, inheriting the global 5-minute default (`constants/ui.ts:11-14`), so even a window-refocus refetch wouldn't help inside that window — consistent with "only a full reload fixes it."
*Fix direction:* T9-T10.

**F2 — No-hot-switch constraint: currently safe, but a real regression risk once F1 is fixed.** Confirmed safe today. Grepped every `setSelectedUser` call site (3 total) — none is a "refetch → auto-select" pattern; `selectedUser` is isolated `useState` in `useMessagesPage.ts:39`, never derived by indexing into `conversations`/`friends`. This is not a bug to fix, it's a guardrail: whoever implements F1's fix must not derive `selectedUser` from the newly-invalidated list data (e.g. `list.find(...) ?? list[0]`), which would silently reintroduce exactly the regression Berkay called out. *Fix direction:* T11 (no code, a constraint on T9).

**F3 — Chat-room doesn't scroll to bottom: sentinel div wired outside the scrollable container.** Confirmed. Both pages share `next-js-boilerplate/src/hooks/useAutoScroll.ts`, which calls `bottomRef.current?.scrollIntoView(...)` and only works if `bottomRef`'s node lives *inside* the `overflow-y-auto` element as its last child. `ChatMessageList.tsx:21-24,57` (Messages page) does this correctly — sentinel is the last child inside the scrollable div. `ChatRoomMessageList.tsx:17-25` (chat-room) renders the scrollable list with **no sentinel inside it at all**; the sentinel is instead added by the parent, `ChatRoomMainContent.tsx:90-99`, as a **sibling** of `ChatRoomMessageList`, inside an `overflow-hidden` wrapper (line 67) — not an ancestor of the real scrolling element. `scrollIntoView()` on a node with no scrollable ancestor has no effect on the actual list. This also means the `isAtBottom` state (same `IntersectionObserver`, watching this same misplaced sentinel) is unreliable, so the floating "scroll to bottom" button likely also fails to appear correctly — a secondary symptom of the same root cause. Not a missing-dependency bug, not a "never ported" gap — specifically a sibling-vs-child DOM nesting mistake introduced when chat-room was built. **Flutter unaffected** — both `chat_view.dart` and `chat_room_base_view.dart` use a `ScrollController` attached directly to the `ListView.builder`, no sentinel div, no analogous mistake possible (code comments in both files suggest a related issue was already found and fixed there). *Fix direction:* T12.

**F4 — Chat nickname: not a caching bug, the feature doesn't exist end-to-end.** Confirmed. `views/settings/privacy/FreePageView.tsx:17-25`'s `handleSave` builds `{hideProfilePicture, useNickname, nickname}` and **never sends it anywhere** — no `fetch`, no mutation call, just an unconditional "Preferences saved" toast. There's also no initial-value fetch, so the toggle/field always start blank. Even if it did save: no nickname/alias field exists on the `User` Prisma model (searched schema + `profile`/`users` broadly); `UpdateProfileInput` only has `name`/`username`/`bio`/`avatarUrl`/`locale`/`timezone`. The presence layer has no slot either — `ws.userName` is set once at socket-auth via `displayName()` (`common/utils/display-name.ts:1-6`, `name || email || 'Unknown'`), and the `RoomMember` type (`messaging.types.ts:1-5`) constructed at both room-join sites in `messaging-ws.gateway.ts:158-162,260-264` has no nickname field. `ChatRoomSidebar.tsx:99-106` renders `{m.name}` verbatim, with nothing to prefer even if it existed. **Flutter has the identical gap**, faithfully ported: `privacy/page_view.dart:57-59`'s `_save()` is the same discard-the-payload toast, and `chat_room_sidebar.dart:130,142` renders the same nameless `RoomMember` shape. *Fix direction:* T13-T18 (backend+web), T21-T22 (Flutter).

### 2.2 Avatar / S3 upload

**F5 — `MINIO_PUBLIC_URL` missing → every returned avatar URL is a Docker-internal hostname.** Confirmed. Storage is real MinIO (not a mock) — `docker-compose.yml` runs a real `minio/minio` container plus a bucket-provisioning job, and backend credentials in `.vault-envs/backend.env` are genuine dev-default creds, not broken placeholders. But `MINIO_PUBLIC_URL` is referenced in exactly one place, `minio.service.ts:22-25`, and is **absent** from the backend's Vault secret — so the fallback `` `http://${endPoint}:${port}` `` always fires, producing `http://minio:9000/uploads/<uuid>-full.webp` for every upload. No browser or mobile device can resolve `minio` as a hostname. Notably, root `.env`/`next-js-boilerplate/.env.local`/the `frontend` Vault secret all define a plausible real value (`NEXT_PUBLIC_MINIO_PUBLIC_URL=https://app.eys.gen.tr/api`) — but it's read **nowhere** in the frontend (zero matches repo-wide), isn't forwarded as a Next.js build arg in `docker-compose.yml` either, and wouldn't matter regardless since the URL is server-generated by `MinioService` and handed to the client in the API response, never constructed client-side. This looks like an abandoned partial fix — the right value exists in three places, just never landed in the one place (`backend`'s Vault secret) that would use it. **Cannot fully confirm** whether the external openresty reverse proxy actually routes `/api/uploads/*` through to MinIO without live/infra access — the chosen value strongly implies someone intended exactly that.
*Fix direction:* T23.

**F6 — Even a hostname fix would be rejected by validation.** Confirmed, verified directly against the installed library (no server run — a pure library call): `UpdateProfileInput.avatarUrl` (`update-profile.input.ts:34-37`) is `@IsUrl()` with no options, and class-validator's default is `require_tld: true`. Tested against `validator@13.15.35` directly:
```
isURL('http://minio:9000/uploads/x-full.webp')                       -> false
isURL('http://localhost:9000/uploads/x-full.webp')                   -> false  (even localhost fails)
isURL('https://app.eys.gen.tr/api/uploads/x-full.webp')               -> true
```
Nest's global `ValidationPipe` (`main.ts:125-132`, `whitelist/forbidNonWhitelisted/transform: true`) genuinely enforces this — the mutation 400s before `ProfileService.updateProfile()` ever runs, so `avatarUrl` never reaches Postgres. **The persistence layer itself is fine** (confirmed: `profile.service.ts:29-69` correctly writes `avatarUrl` and mirrors it into the Redis session hash) — nothing ever reaches it because of F5+F6 stacked together. Compounding UX problem: the GraphQL error is correctly shaped server-side (`extensions:{exc,msg,key,fields}`) but the frontend's `graphqlErrorBody()` (`lib/backend.ts:220-230`) only surfaces the generic top-level `msg` ("Validation failed"), dropping the field-specific reason — so even the one path that *does* throw visibly gives no hint this is upload/avatar-related. On the client: `Avatar`'s `onError` fallback to initials (`avatar.tsx:60-68`) fires silently with zero console signal for the browser-can't-resolve-hostname case, explaining "nothing appeared to happen" precisely. One dead no-op found in passing: `useProfileActions()` calls `queryClient.invalidateQueries({queryKey:["profile"]})` after upload/update, but nothing anywhere subscribes to that query key (`FreePageView.tsx` fetches via a raw `useEffect`, not react-query) — harmless, but worth cleaning up while in this code.
*Flutter*: shares F5+F6 exactly (same backend endpoints via Dio). Additionally has its **own** separate bug: `_profileProvider` (`page_view.dart:18-21`) is never invalidated after a successful save — even a backend fix wouldn't show the new avatar on that screen without navigating away and back. Flutter also auto-saves on pick (unlike web's explicit-Save flow) and shows an immediate `showToast('Failed: $e')` on error — a real, useful behavioral divergence from web's silent failure, worth keeping.
*Fix direction:* T24-T26 (backend+web), T27 (Flutter).

### 2.3 New features (greenfield feasibility)

**F7 — Message file attachments: fully greenfield, two composers on two different transports.** Confirmed. `Message`/`RoomMessage` Prisma models have only `body String` — no attachment field (`Post`/`Comment` elsewhere use a simple `imageUrl String?` convention worth mirroring rather than a new relational table). `/v1/en/messages` uses `ChatInputBar.tsx`, which **already has a disabled, dead paperclip button** (lines 88-95, no `onClick`) — sending goes over REST (`messaging.controller.ts:178-192`). `/v1/en/chat-room` has an entirely separate composer (`ChatRoomSubComponents.tsx`) with **no attach affordance at all**, sending over WS (`messaging-ws.gateway.ts:191-219`) — so this can't be a single shared fix. The upload module (`upload.controller.ts:25`) is hardcoded to an image-only allowlist and forces every upload through `ImageService.resize()` — no notion of "purpose," so non-image attachments (PDF, docs) can't go through today at all. Interesting tell: Flutter's `constants/upload.dart` already defines `allowedDocumentTypes` that nothing backend-side currently honors, suggesting this was anticipated once and not finished.
*Fix direction:* T28-T34 (backend+web), T37 (Flutter).

**F8 — Emoji picker: fully greenfield on both platforms, nothing to adapt.** Confirmed. Zero emoji-related npm dependency in `next-js-boilerplate/package.json`, zero existing picker component (even unused/demo) in `components/ui/`. The only "emoji" hits anywhere are `ReactionButtons.tsx`'s 4 hardcoded fixed reaction emoji (👍❤️😂😮) — a fixed reaction-selector, structurally unrelated to a free-text insertion picker (no search/categories/unicode dataset). Same on Flutter: no emoji package in `pubspec.yaml`, no picker widget in `lib/components/ui/`. Neither composer (messages or chat-room, either platform) has any emoji affordance today.
*Fix direction:* T35-T36 (web), T38 (Flutter).

### 2.4 Settings/Sessions

**F9 — "No active sessions found" is caused by a blanket error-swallow, not necessarily an empty result.** Confirmed as the proximate cause. `views/settings/sessions/FreePageView.tsx:51-64`'s fetch is wrapped in `try { ... } catch { setSessions([]); }` with **no logging, no telemetry, nothing** — any failure at all (network error, GraphQL error, 401, 500) renders the exact same `EmptySessions.tsx` ("No active sessions found") as a genuine zero-sessions state. The `session`(singular)/`sessions`(plural) split was checked and resolved: `session/` is a dead, unimported NestJS-docs tutorial module; `sessions/` (via `SessionsResolver`) is the real, wired-in feature, and `mySessions` has no duplicate/shadow resolver. Cookie names, header names, and the frontend/backend `SessionInfo` field shapes all match — those plausible theories were checked and ruled out.
*Most likely underlying trigger (Plausible, needs live verification):* `SessionsResolver.mySessions()` (`sessions.resolver.ts:48-76`) makes an **unguarded** `prisma.device.findMany(...)` call inline, with no try/catch, purely to enrich the response with a "Trusted" badge. If that throws for any reason (DB blip, pool exhaustion), it kills the *entire* response — a best-effort enrichment taking down the primary feature. This exact interaction is untested (the resolver's own spec mocks `tokenStore.listSessionsWithKeys` directly and never exercises the Prisma call). Confirming this is actually firing needs live backend log tailing during a repro.
*Fix direction:* T39-T40.

**F10/F11 — Independent, confirmed bugs found in the same area, worth fixing regardless of F9's exact trigger.** Confirmed. (a) `TokenStoreService.extendTTL()` (`token-store.service.ts:148-151`) only slides the main session hash's Redis TTL — the parallel `refresh_sess:<sessionId>` reverse-index key (needed to redeem a refresh token) is set once at login/refresh and never renewed, so a continuously active user's *session* stays alive indefinitely but their ability to *refresh* silently dies after `SESSION_TTL` (default 900s) regardless of activity. This directly undermines Stage A's auth-loop fix if it starts relying on the real refresh mutation — must be fixed together (see F3 in the executive summary). (b) The reverse-index Redis `SET` (`user:<id>:sessions`) is never independently expired — stale members accumulate forever (doesn't cause wrong results, since dead sessions are filtered at read time, but it's unbounded growth). (c) `api/server/sessions/list.ts:4-12` declares its own local `SessionInfo` type with a phantom `expiresAt` field the backend never returns, reconciled only via an `as unknown as` cast that defeats type-checking. (d) The sessions-list BFF route omits `noCache: true` on its `graphqlFetch` call — same cross-cutting caching-default gap called out in the executive summary; `api-keys/route.ts` has the identical gap.
*Fix direction:* T41-T44.

**F12 — Device type is already computed backend-side, just never exposed; IP is already both captured and rendered; "current session" badge is already fully built end-to-end.** Confirmed, and good news on two of three fronts. IP: `main.ts:108` sets `trust proxy: 1`, `session.ip` is already in the GraphQL type and already rendered (`SessionCard.tsx:63-68`) — nothing to do here beyond confirming prod's proxy topology is exactly one hop (can't verify statically). Device type: `device.service.ts:47-65`'s `detectDeviceType()` already computes a clean enum (`WEB`/`MOBILE_IOS`/`MOBILE_ANDROID`/`DESKTOP`/`API`/`CLI`) and stores it on `Device.type` — but `mySessions()`'s Prisma call only selects `{id, trusted}`, and the GraphQL type has no `deviceType` field, so the frontend falls back to crude UA-string-sniffing (`SessionCard.tsx:18-21`) and just truncates the raw UA as a "device name." This is a pure wire-up task, not new data capture. (`Device.name String?` exists in the schema but is never populated anywhere — a dead column if a human-readable "Chrome on MacBook" label is wanted later, out of scope here.) Current-session badge: **already fully implemented** — `auth.resolver.ts:148-166`'s `me` query returns `sessionId`, `FreePageView.tsx:79,111` already computes `isCurrent`, and `SessionCard.tsx:51-98` already renders the badge/border/hidden-revoke-button. This should just start working once F9 is fixed — do not rebuild it.
*Fix direction:* T45 (device type wire-up only); T46 is a verify-only checkbox, no code.

### 2.5 Settings/Billing

**F13 — Critical: paid→paid upgrades never cancel the prior Stripe subscription.** Confirmed. `billing.service.ts:56-169`'s upgrade branch never checks `user.stripeSubscriptionId` and never calls `cancelSubscription()` before creating a new one — that logic exists only in the *downgrade* branch. BASIC→MEDIUM creates a second live Stripe subscription and overwrites the single `stripeSubscriptionId` column (line 108), permanently losing the reference needed to ever cancel the first one in-app. The customer is billed for both, forever. Untested: upgrade specs (`billing.service.spec.ts:106-172`) all start from `FREE`, never from an existing paid tier.

**F14 — Weak idempotency on two independent axes.** Confirmed. `generateIdempotencyKey()` (`billing.service.ts:442-448`) buckets by **60-second** wall-clock windows — a double-click even slightly more than a minute apart produces two different keys, no protection past that window. Within the window it's a classic TOCTOU race: `findFirst` for an existing key, then a full Stripe round-trip, then the write — two concurrent requests can both pass the check before either commits. No Stripe-side `idempotencyKey` request option is passed either, so there's no provider-level backstop.

**F15 — Stripe charge and local state aren't atomic across a crash window, and the webhook doesn't reconcile.** Confirmed (partially good news, partially not). The tier-update and wallet-ledger write *are* correctly wrapped in one `$transaction` together (`billing.service.ts:103-143`) — but that transaction runs *after* the Stripe charge already succeeded. A crash in that gap leaves Stripe billing live with zero local record. The `invoice.paid` webhook (`stripe-webhook.controller.ts:92-169`) fires independently but only updates `subscriptionPeriodEnd`/`stripeSubscriptionId` — **it never touches `subscriptionTier`** — so there's no reconciliation path for this exact gap.

**F16 — Likely duplicate invoice rows per upgrade.** Confirmed as a structural risk. The synchronous path writes a `$0`/`stripePaymentIntentId: null` `WalletTransaction` (`billing.service.ts:113-130`, key scheme `sub:<user>:<tier>:<minuteBucket>`); the async `invoice.paid` webhook writes its *own* `WalletTransaction` for the same event with a completely different key scheme (`stripe_invoice:<invoiceId>`) and no cross-reference to the first. `getBillingHistory()` has no dedup logic, so both rows surface in `myBillingHistory` — a user upgrading likely sees two line items for one purchase, one showing $0.

**F17 — Currency double-division: invoice amounts wrong by ~100x.** Confirmed. `stripe-webhook.controller.ts:97`: `Math.round(invoice['amount_paid'] / 100)` treats Stripe's cents as if converting to whole dollars (also rounding away the cents). `InvoiceTable.tsx:98` then does `` `$${(tx.amount/100).toFixed(2)}` `` — dividing by 100 *again*, assuming the stored value was cents. Given real configured prices (`$9.99`/`$19.99`/`$49.99`, all X.99), a $19.99 charge stores as `20` and renders as **$0.20**. The rest of the codebase's own convention (`lib/currency.ts`'s `formatPrice(cents,...)`, `lib/tier.ts`'s `TIER_PRICES_CENTS`) is "store cents, format at render" — the webhook handler is the one place that deviates from its own codebase's convention. Zero test coverage exists for `stripe-webhook.controller.ts` at all, which is how this went uncaught.

**F18 — "Best-effort" Stripe cancellation can silently diverge from reality.** Confirmed. Both `cancelSubscription()` and the downgrade branch catch-and-log any Stripe cancel failure, then **unconditionally** proceed to write local `cancelAtPeriodEnd: true` regardless. If the Stripe call actually failed, the app tells the user "cancellation scheduled" while Stripe keeps auto-renewing and charging — no retry, no reconciliation, no user-facing indication of the mismatch.

**F19 — Downgrade access-cutoff timing is inverted; paid→paid downgrade never provisions the replacement subscription.** Confirmed. The downgrade branch drops the app-side tier **immediately** while the Stripe subscription (still at the old, higher price) is only flagged `cancel_at_period_end: true` and keeps billing until the period naturally ends — the customer loses access to what they're still paying for, the inverse of the usual "keep access through what's already paid for" pattern. Separately: if the target is still a paid tier (e.g. PREMIUM→BASIC, not →FREE), the code only cancels the old subscription and never creates a correctly-priced replacement — once the old subscription lapses, the account sits on a "paid" app tier with zero active billing, indefinitely.

**Billing restructure (2b/2c), confirmed straightforward:** Invoices currently render as a third full-width block stacked directly beneath the two-column Plan/Payment/Address region (`views/settings/billing/FreePageView.tsx:52-100`) — confirming the "squeezed in" framing exactly. **F21 — THE auth loop, primary mechanism: the automatic-logout path never clears cookies.** Confirmed, traced end-to-end, file:line at every step:
1. Some authenticated request 401s for real (see F23 for concrete triggers) via `SessionAuthGuard`.
2. `apiFetch()` (`lib/api-client.ts:18-29`) sees the 401 and does `window.dispatchEvent(new CustomEvent("auth:logout"))`.
3. The only listener, `onAuthLogout` (`features/auth/hooks/useAuth.tsx:113-130`):
   ```js
   function onAuthLogout() {
     if (logoutEventRef.current) return;
     logoutEventRef.current = true;
     setUser(null); setToken(null);
     const path = window.location.pathname;
     if (path !== "/auth/login" && !path.startsWith("/auth/")) {
       window.location.href = "/auth/login";
     }
   }
   ```
   This clears **only in-memory React state** and hard-navigates. It never calls `logoutServer()`/`/api/auth/logout`, so `access_token`, `rbac_token`, `device_token`, `user_token`, and **`session_user`** all survive completely intact.
4. Fresh full-page load on `/auth/login`. `app/auth/login/page.tsx:15-19`'s server-side check, `getSessionUser()`, finds the still-present `session_user` cookie, **blindly decodes it with no signature/expiry check**, returns a non-null user → immediately `redirect('/v1/en/feed')`.
5. Back on `/v1/en/feed`: `proxy.ts:157` (this app's Next.js middleware — the file is named `proxy.ts`, not `middleware.ts`, per Next 16's renamed convention; there is no `middleware.ts` anywhere in the repo, confirmed via `git log --all`) only checks *presence* of `access_token`, not validity — passes through. `app/v1/[lang]/layout.tsx:16-18` calls the same blind `getSessionUser()` → renders normally, mounting a **brand-new** React tree (full reload resets `logoutEventRef.current` to `false`).
6. The freshly-mounted feed page's queries hit the backend guard again, fail for the *same underlying reason as step 1* (nothing backend-side changed), the whole sequence repeats.
7. The loop only breaks when the shared 15-minute cookie Max-Age finally elapses (counted from original login, unrelated to when the loop started) or the user manually clears cookies.
This is exactly Berkay's own diagnosis — "token/session residuals — it believes session is still active but it is not" — with the specific residual now identified precisely: `session_user` (and its siblings) surviving a logout path that was only ever written to manage client memory, never server-side cookie state. **Mostly deterministic, not a race** — the `logoutEventRef` dedup guard correctly collapses multiple concurrent 401s into one navigation; the actual defect is an incomplete operation (missing cookie-clear step), not two operations racing.

**F22 — The "refresh" mechanism doesn't refresh; the real one is never called.** Confirmed. `useAuth.tsx:86-92` calls `refreshTokenServer()` → `/api/auth/token` (`app/api/auth/token/route.ts`), whose entire body reads the current cookies and echoes them back as JSON — **no backend call of any kind**, cannot mint a new token or detect an expired one. Meanwhile the backend has a fully correct, already-implemented `refresh` GraphQL mutation (`auth.resolver.ts:72-76` → `auth-session.service.ts:52-138`) that correctly revokes the old session and — since the `c0982fa0` fix — correctly carries device identity into a fresh token issuance. Repo-wide grep for a `refresh` GraphQL mutation call from the web frontend: **zero matches.** It's also structurally unreachable even if wired naively: the BFF's login query never requests a `refreshToken` field, and `lib/cookie.ts` has no `REFRESH_TOKEN_COOKIE` concept at all — the value needed to call `refresh` never reaches the browser in the first place. Net effect: **there is no code path that can silently repair a stale web session.** A landmine found in passing: a second, dead-looking file `api/server/auth/refresh-token.ts` exports the *same* function name `refreshTokenServer` with a different signature — `useAuth.tsx` imports from `token.ts`, not this one, but the naming collision is a hazard for future edits.

**F23 — Concrete, code-confirmed triggers for a "valid-looking" cookie to disagree with the backend.** Confirmed (a, b); Plausible-but-real-mechanism (c, needs live check). (a) **Tier change during an open session** — `billing.service.ts:145,234` call `tokenStore.rewriteFieldsForUser(userId, {tier})` on every upgrade/downgrade, which immediately HSETs the new tier onto *every* live Redis session for that user. The guard's step-5 check recomputes `deriveRbacToken(userId, tier)` fresh from that Redis value — the very next authenticated request after a plan change has a guaranteed mismatch against the `rbac_token` cookie (still derived from the old tier at login), 401ing on the spot, cookies otherwise untouched and still within their 15-minute Max-Age. `useAuth.tsx:200-213`'s `onTierChanged` WS handler exists specifically to keep the UI in sync post-tier-change but only refetches the *display* user object — never touches the `rbac_token` cookie, so it doesn't prevent this. Directly relevant: the billing page under investigation in Stage F is exactly the trigger for this. (b) **UTC-midnight derivation cutover** — `TokenDerivationService.dateOnly()` truncates to the UTC calendar date for both `user_token` and `rbac_token`; any session opened in roughly the last 15 minutes before UTC midnight has cookies still present past midnight but derived for "yesterday," rejected as "Daily token expired." (c) Explicit session revocation while local cookies persist — a real mechanism (`revoke`/`revokeAllForUser`), not confirmed to currently misfire; would need a live check.

**F24 — The explicit "Sign out" button has a milder, related bug.** Confirmed. `logout()` (`useAuth.tsx:185-189`) correctly `await`s `logoutServer()`, which properly clears all 5 cookies server-side regardless of whether the backend revoke succeeds. But **nothing downstream navigates anywhere** — confirmed at every call site (`ProfileDropdown.tsx:49-53`, `ProfileSection.tsx:60-64`, both fire-and-forget, no `router.push`/`redirect` in the chain). Clicking "Sign out" correctly clears everything server-side but leaves the user staring at the same URL until some component's own inline `if (!user)` check happens to kick in. Not a loop, but the same family of bug: an auth transition that's incomplete about the "then what" step.

**F25 — Two recent commits already attempted a narrower, related fix; never verified.** `3aff834d`/`c0982fa0` (2026-07-28, both **after** convert-frontend-9's doc closed clean, so outside any verification round in that doc) fixed a session-key-mismatch specific to the MFA-verify path: `verifyLoginMfa` previously called `issueTokens(user, ctx)` **without resolving device context**, unlike every other login path — meaning a successful MFA login could mint a session keyed on an empty device-token slot the next real request could never match. The fix (peek-not-consume the MFA challenge + `this.devices.resolveForLogin(...)` before `issueTokens`) is now consistent with all 4 other `issueTokens` call sites (checked directly: `login()`, `loginWithOAuth()` ×2, `refresh()` — all correctly resolve/carry device context today). Ran `npx jest src/auth/auth.service.spec.ts src/auth/auth-session.service.spec.ts` live this session: **20/20 pass.** This is a real, distinct fix from F21/F22 — it addresses one specific call site's device-context bug, not the general cookie-cleanup gap. Both should be swept into the same verification pass since they're both in the auth trust chain, and this one was never independently confirmed live (only via unit tests, which mock heavily).

**Flutter comparison — structurally not affected by F21/F22.** Confirmed. `AuthNotifier` (`hooks/use_auth.dart`) is a single `StateNotifier`, watched identically by the router's redirect guard, the Dio interceptor, and every widget — one source of truth, can't disagree with itself the way web's proxy/layout/React-context triad can. `AuthInterceptor.onError` (`lib/lib/api_client.dart:88-130`) already catches 401s and calls a real `refreshAccessToken()` that hits the backend's actual refresh endpoint and persists rotated tokens — a real, working refresh flow. **This directly contradicts the `flutter-conversion` skill doc's current claim ("There is no token-refresh flow yet")** — that's stale, worth correcting (T70). *Fix direction:* T1-T8.

### 2.7 Feed comments

**F26 — Replies are structurally excluded from the feed's post query — permanent, not timing-dependent.** Confirmed. `PostService.findOne()` (`post.service.ts:185-243`) queries `comments: {where: {deletedAt:null, parentId:null}, ...}` — an unconditional filter that can never return a reply, at any TTL, after any number of reloads — and doesn't even `select: {parentId:true}`, so the field wouldn't come through even if the filter were relaxed naively. The Prisma schema and GraphQL model both correctly support replies (`Comment.parent`/`replies`, `@@index([parentId])`); this one query just doesn't use them. **The backend already has a correct query**: `CommentService.findByPost()` (exposed as `postComments(postId)`) properly nests replies — but grep confirms the web app **never calls it**, only the broken `post(id){comments{...}}` path. Client-side symptom: an optimistic reply renders immediately, then is removed the instant the mutation resolves and never replaced, since the follow-up refetch can structurally never contain it — a user watches their own reply vanish. (A second reply to the same parent then 409s as a duplicate, since the first one *did* persist — a likely source of real user confusion worth noting.)

**F27 — Three-layer, unbusted cache stack sits in front of the same read path, and the feed page specifically has no working invalidation at all.** Confirmed. Layer 1: the BFF GET route sets `Cache-Control: public, max-age=60, stale-while-revalidate=120` (`app/api/posts/[id]/route.ts:38-45`) — a real browser cache hit is likely given the natural "expand comments → post → recheck" flow. Layer 2: that route's own outbound `graphqlFetch` call omits `noCache`, taking the `next:{revalidate:60}` branch — this is server-side and **invisible to a browser reload**, directly explaining "not even after a full reload." Layer 3: the backend's Redis cache-aside (`PostService.findOne`) *is* correctly invalidated by both `create()`/`update()` (`comment.service.ts:70-71,107-108`) — not itself broken, just dominated by layers 1-2 which are never invalidated on any timescale shorter than their TTL. Compounding, feed-page-specific problem: `PostCard.tsx`'s `postData` is plain `useState`, not react-query-observed — so neither the manual invalidation (`usePostActions().invalidate()`, only touches `["feed"]`/`["posts"]` prefix keys) nor the realtime-driven one (`{renew:'Feed',type:'Post',id}` → `qc.invalidateQueries({queryKey:["posts",id]})`) ever reaches it, since nothing on the feed page observes that query key at all — `refetchType:"active"` is a no-op against zero active observers. Both invalidation paths *do* correctly exist and *do* fire — they're just aimed at a query nothing on this specific page mounts. (The standalone `/posts/[uuid]` detail page is wired correctly against the matching key, but ultimately calls the same poisoned two-layer read path, so likely shows the same staleness for a shorter effective window.)

**F28 — Edit doesn't refresh because the mutation's own response is discarded, then the same poisoned refetch runs.** Confirmed. The backend's `update()` (`comment.service.ts:85-120`) is real — ownership-checked, calls Prisma's `.update()`, returns exactly the shape the frontend's mutation requests, and is covered by a passing unit test. The frontend's `updateCommentServer` (`api/server/posts/comments.ts:22-35`) never reads or returns the response body at all (`Promise<void>`) — there's no cache reconciliation of any kind for this app's data layer (react-query, but this state isn't under it per F27). The only path back to fresh data is the same `onCommentAdded()` → `refreshPost()` refetch F26/F27 already poison. Second-order effect worth noting for the exact reported symptom shape: `CommentSection.tsx`'s optimistic `localEdits` overlay shows the new text immediately, the mutation succeeds, the overlay clears, then the un-awaited stale refetch resolves and overwrites parent state with the *old* text — a user perceives "my edit didn't save" when it actually did; the read path lied about it.

**F29 — Apollo Federation ruled out.** Confirmed, a dead end. `app.module.ts` wires a single plain-`ApolloDriver` `GraphQLModule` (not `ApolloFederationDriver`); `federation/posts-subgraph/` is a self-contained, unrelated NestJS-docs example backed by a hardcoded in-memory array of 3 fake posts, with its own separate `GraphQLModule.forRoot`, never imported into the real `AppModule` bootstrap. No subgraph boundary exists in the live system — not a contributing factor.

**F30/F31 — Flutter shares the symptom shape, not the mechanism.** Confirmed. Flutter talks directly to the backend over Dio with no BFF layer, so F27's caching stack doesn't exist on mobile — but `postComments`'s Dart-side GraphQL selection (`api/server/posts/comments.dart:10-21`) only asks for `{id,body,authorId,postId,createdAt,updatedAt}` — no `parentId`, no nested replies — so replies are invisible on mobile too, for a client-query-gap reason rather than a backend-filter reason (the Dart model already has a `parentId` field, just unpopulated — an easier fix than web's, since the backend query Flutter already calls is the *correct* one). Separately, none of the three comment-mutation call sites (`add`/`update`/`delete` in `api/client/posts/actions.dart:51-67`) ever call `ref.invalidate(postCommentsProvider(...))` — the **only** thing that can refresh that provider is a realtime WS push (`realtime_provider.dart:60-92`, correctly wired when it fires). This makes Flutter's comment refresh realtime-or-nothing: correct and immediate when the socket is live, silently stale if the socket is down/reconnecting at the moment of the mutation — a plausible explanation for an intermittent-on-mobile-specifically version of this bug, flagged as needing a live WS-traffic check to confirm reliability.
*Fix direction:* T58-T62 (backend+web), T63-T64 (Flutter).
